# Implementation plan

Use one eve agent. Configure model access through eve, pin and record the provider and model for evaluations, and keep the credential in the controller. Use eve's custom tools directly. Use the same agent definition with separate sessions and tools for intake/attempt, diagnosis and independent replay. A second fx agent would still require us to implement provisioning and evidence capture. Relevant APIs are described in the [eve tools guide](https://eve.dev/docs/tools) and [sandbox guide](https://eve.dev/docs/sandbox).

1. **Offline evidence contract.** Write synthetic acceptance cases for a successful guide, wrong filename, missing outcome after exit zero, unsupported environment and platform failure. Implement a pure verdict function and Markdown receipt using these examples. Keep judgments independent of model prose. Run the tests without a network, provider or credentials.
2. **Read and propose.** Resolve the repo revision and provide README and explicitly linked guides to eve. Have the agent propose an ordered plan containing cited steps, documented starting prerequisites, install instructions, access needs and an observable check. Preserve the source bytes for references, including external guides. Distinguish an ambiguous promise from a missing instruction. Resolve the request against a repository-independent catalog without creating a VM. Show the immutable image identity, revision, exact commands, required access and frozen check for approval. Test an unsupported runtime (receipt without a VM), ambiguous paths (record what the docs leave unclear), and declined approval (no execution or documentation verdict). Compare derivations from contrasting Python and Node guides without supplying a repository profile.
3. **Provision and execute.** Give eve a tool to request an environment based on the cited prerequisites. After verifying approval of the resolved plan, the controller creates one fresh nonpersistent Vercel Sandbox microVM for the attempt. Documented installs run as steps. Keep credentials outside the guest. Expose a tool for running only the next approved step on the assigned VM, including documented tests. Preserve shell state, directory and running services across steps. Stop on failure or ambiguity, record remaining steps as unrun, and bound time, output, network access and spend. Confirm teardown even on error. Inspect the effective tools and resource lifecycle. Verify that the agent cannot use an alternate shell, file reader or network path and eve does not create an extra sandbox. First exercise one dependency-free step under the separately approved infrastructure budget in the roadmap.
4. **Terminal integration.** Connect intake, plan approval, execution and a controller-owned observer. Verify prerequisites and preconditions (such as file absence), then check the promised effect. Use the same deterministic record for terminal and Markdown output. Separate an absent result from a failed observer and distinguish a suspected docs gap from an app defect. Force a summary error in a test and verify that the saved receipt survives. Evaluate two dissimilar repositories through the same entry point, including environment selection, a file check and a service check. Compare actual image and commands with the approved plan.
5. **Diagnosis and replay.** After a supported blocker, allow a separate diagnosis session to inspect source and propose a minimal docs edit. Start a fresh newcomer session and VM on the original base image. Exclude prior transcripts and caches. Match the original revision and access rules. Keep the outcome check fixed, derive steps from the revised guide, and compare dependency and artifact identities. Require an original failure and independent comparable pass before labeling any edit verified. Exercise changed artifacts, unchanged docs and leaked state as negative controls.
6. **Demonstrate the workflow.** Present a measured receipt, label synthetic examples, redact output and follow the roadmap’s submission checks.
